## 2. 무작위 순차 배치의 실제 용량

`capacity.py`·`capacity_grid.py`의 결과다. 일반 등급만 썼다. N99는 "N개 전부 놓일 확률 ≥ 99%"인 가장 큰 N이다.

| 방식 (z 1.0, s 0.7, 장치 없음) | N99 | 막힐 때까지 평균 |
|---|---|---|
| 무작위 30번 (지금) | 12 | 20.5 |
| 무작위 60번 | 12 | 21.0 |
| 무작위 100번 | 14 | 21.1 |
| **무작위 30번 + 실패 시 8px 격자 빈 점 중 무작위** | **19** | 21.9 |

같은 비교를 z 1.35, s 0.55에서 하면 N99는 8 / 10 / 10 / **13**이다.

- **시도 횟수를 늘려도 보장 개수는 거의 안 는다.** 마지막 몇 개는 빈 곳이 필드의 1~3%뿐이라 100번으로도 못 찾는다.
- 실패할 때만 격자를 훑으면 막힘(jamming) 직전까지 채운다. 이 방식을 제안한다.
  - 비용: z 1.0에서 격자 점 약 1.7만 × 군락 ≤ 20, 실패할 때만 든다.
- 채움률 φ99(= N99 · π(RR+5)² / 놓을 넓이)는 격자 보충 기준 **0.36~0.47**이다. 작은 필드에 큰 군락이면 가장자리 손실로 0.2~0.3까지 떨어진다.
- 장치 3개는 md_map L0에서 치명적이다. s 1.0이면 평균 0.8개만 놓인다(지금 코드에서도 같다. 측정표는 장치 없음).

## 3. 크기 조절 규칙

### 3-1. s의 하한 (보이기·맞히기)

- 화면 px = 필드 px × z다. 군락 버섯 지름은 화면에서 등급별로 `2·r·s·z`가 된다.
- 하한은 레전드리(r 20)의 화면 지름 ≥ **28px**(1920×1080 기준)로 잡는다. 이때 일반(r 32)은 ≥ 45px다.
- 그 위에 필드 px 하한을 둔다. 일반 r ≥ 14.4는 기본 핀볼 반지름 27의 절반 남짓이다.

```
s_min(z) = max(COL_S_VIS / z, COL_S_ABS),   COL_S_VIS = 0.70, COL_S_ABS = 0.45
```

| md_map | z | s_min | 일반 화면 지름 | 레전드리 화면 지름 |
|---|---|---|---|---|
| L0 | 1.68 | 0.45 (바닥) | 48px | 30px |
| L1 | 1.5 | 0.467 | 45px | 28px |
| L2 | 1.35 | 0.519 | 45px | 28px |
| L3 | 1.2 | 0.583 | 45px | 28px |
| L4 | 1.1 | 0.636 | 45px | 28px |
| md_map2 | 1.0 | 0.70 | 45px | 28px |

- **맞히기:** 같은 필드에서 버섯이 작아지면 핀볼 한 개가 군락 하나를 맞히는 단면이 줄어 `(r_b + 32)/(r_b + 32s)`배로 맞히기 어려워진다(r_b = 27×ps_size). s 0.72, r_b 35이면 ×0.85다. 대신 군락이 많아져 필드 전체 단면은 늘어난다. 5절 수입 근사에 넣었다.
- **28px 하한은 판단값이다.** 모바일 가로 화면이면 더 키워야 할 수 있다(9절 불확실).

### 3-2. 공식 (판마다 한 번, 장치를 놓은 뒤·군락을 놓기 전)

```
A_free = (FX1 − FX0)·(NO_SPAWN_Y − FY0) − π·140²/2 − Σ 장치 넓이        // 그루터기 π·56², 이끼 364·70, 도토리 3·π·18²
ρ      = sqrt(COL_PACK · A_free / (π · MaxCol))                          // 군락 하나 몫 반지름(여백 반 포함)
s0     = clamp((ρ − 17) / (3.9 · R_REF), COL_S_ABS, 1)                   // RR+5 = 3.9·r·s + 17 을 거꾸로 푼 것
R_REF  = TIERS[0].r (= 32, 가장 큰 일반 등급)
```

**놓기** (`proposal.py` `run_prop`)

1. 종을 MaxCol개 먼저 고른다. 난수 순서는 지금처럼 군락마다 벽 확률 → 종 → 둘레 수다.
2. s = s0에서 위치만 계획한다.
   - 군락마다 무작위 COL_TRIES(30)번 시도한다.
   - 다 실패하면 COL_GRID(8px) 간격 격자에서 빈 점을 모두 모으고, 그중 하나를 `U.RandI`로 고른다.
3. 다 놓이면 그 위치로 CreateColony를 하고 끝낸다.
4. 못 놓은 게 있으면 `s ← s × COL_SHRINK(0.93)`로 처음부터 다시 계획한다.
   - s_min(z)를 건너뛰지 않고 한 번 들른다.
   - COL_S_ABS에서 멈추고, 그때는 놓인 만큼만 만든다.
   - 남은 것은 지금처럼 재생 대기열로 간다.

**정한 것**

- **등급별로 같은 s를 쓴다.** 등급 사이 크기 비(32:28:22:20)를 그대로 지켜 그림 규칙이 안 깨진다. 공식의 기준 r은 가장 큰 일반 등급(32)이다. 에픽 이상이 섞이면 실제로는 여유가 생긴다(보수적).
- s는 판 안에서 고정이다. 재생(SpawnColony(false))도 같은 s와 같은 "30번 + 격자 보충"을 쓴다.
- 튜토리얼 lone 판과 보스 판은 s = 1로 그대로 둔다.
- COL_PACK 0.40은 시작 추정값일 뿐이다. 공식이 넉넉하게 잡아도 4단계가 줄여 맞춘다. 모델에서 단계 4는 평균 0~2번 돈다.
- 그림·체력 막대·그림자는 `m.r`을 따라가므로(`ShroomView.cs:70~106`) 따로 고칠 것이 없다.

## 5. 판 수입 영향 (흐름 근사)

```
판 수확 ≈ c · m · T / (t_c + t_r + 0.175)
```

| 기호 | 뜻 |
|---|---|
| c | 필드 위 군락 수 |
| m | 군락당 버섯 수(1 + 둘레 평균) |
| T | 판 시간 |
| t_c | 군락 하나를 비우는 시간 |
| t_r | 다시 나는 시간 |
| 0.175 | 자라서 맞을 수 있게 되는 시간 |

**지금 값과 새 값**

- **지금:** 최대치 > 놓인 수면 t_r ≈ 0.25(대기열)이고, 아니면 st.regen이다.
- **새 규칙:** 다 놓이므로 대기열이 없고 t_r = st.regen(비 ½)이다.

## 9. 불확실한 점

1. **수입 근사가 거칠다.** 흐름식 하나에 t_c를 단계마다 한 점으로 역산했다. 봇 노드 상태(md_map·ed_cols·ed_regen 레벨)는 로그에 없어 가정했다. 단계별 비는 ±30%로 읽을 것.
2. **6~13 ×1.36~×1.69는 가장 크다.** 그 구간에 md_map L1인지 L2인지에 따라 달라진다(L2면 지금 실제 4.5라 덜 오름).
3. **28px 하한은 판단값이다.** 모바일 가로 1080p 화면에서 28px는 약 2mm다. 레전드리가 작아 안 보이면 COL_S_VIS를 0.8로 올린다. 그러면 B ≤ 11이 되어(모델: B 11 전 조합 통과, B 12는 z 1.0에서 s < s_min) ColCount 4·6·7·8·9 + II 1·2 정도로 다시 맞춰야 한다.
4. **배치 MC 난수는 numpy다.** 게임(UnityEngine.Random)과 분포는 같고 수열은 다르다. 장치·발사점·겹침 규칙은 코드를 그대로 옮겼다.
5. **떠도는 군락**(wanderP 0.08)과 거대 버섯(r 90)이 판 중에 자리를 막는 효과는 넣지 않았다. 재생은 같은 "30번 + 격자"를 쓰므로 막힘은 짧을 것으로 본다.
6. **s가 작아질 때 맞히기 어려움**은 단면 비로만 넣었다. 사람의 조준 체감(작은 버섯을 노리기)은 측정이 없다.
