## Z-0. 기준 수입 — 이미 있는 것과 새로 필요한 것
- **판 골드: 이미 있음.** `SaveData.lastNormalGold`(`Assets/Scripts/Core/Save.cs` 36줄, 로드 검증 200줄)를 쓴다. `RoundSim.Effects.cs` `Finish()` 386줄에서 `if (!BossRound && !aborted) G.lastNormalGold = scoreGold + bonus;`로 기록한다.
  - 보스 판은 들어가지 않는다. 보스 스테이지에서 도전을 끄고 하는 파밍 판은 들어간다(같은 스테이지 수입이라 맞다).
  - 중간에 끝낸 판도 들어가지 않는다. 그래서 "짧은 판으로 기준을 낮추거나 바꾸는" 일이 없다.
  - 일부러 못한 판은 기준을 낮추기만 한다. 플레이어에게 이득이 없으므로 악용할 곳이 없다.
- **판 시간: 저장되지 않음.** `st.duration`·`RoundSim.timeMax`는 판 안에서만 있다. `G.play`는 누적 플레이 시간이라 판 하나의 시간으로 쓸 수 없다. 그래서 **새 세이브 필드 1개**를 제안한다.
  - `public double lastNormalSec;` — 직전 일반 판의 제한시간(초) = 그 판의 `timeMax`
  - `lastNormalGold`와 같은 줄에서 함께 기록한다.
  - 판 간격은 프로젝트 규칙(한 판 = 라운드 시간 + 30초)에 따라 코드 상수 `WT.bagRoundGap = 30`을 더한다.
  - DB 칼럼이나 DB Const는 아니다.
- 대안으로 판 시간 없이 `ComputeStats().duration`을 매번 계산하는 방법도 있다. 하지만 날씨·테마 인자가 필요하다. 그리고 `BagRate()`는 밖 화면 틱마다 불리므로 너무 무겁다. 그래서 버렸다.

## Z-1. 공식 (코드에 옮길 이름 그대로)

```
playGoldPerSec = G.lastNormalGold / (G.lastNormalSec + WT.bagRoundGap)          // 기준 플레이 골드/초
raw            = (지금 BagRate 골드/초에서 WT.bagMul만 뺀 값)                         // 꼬마·각성·호감·장식·나이테·gm_herb·treeGold 모두 반영
x              = raw * 3600 / WT.bagRefGoldH[단계-1]                                  // 기준 배치 대비 효율
EffTerm        = raw <= 0 ? 0 : (x <= 1 ? x : Math.Min(WT.bagEffMax, Math.Sqrt(x)))
보따리 골드/초  = playGoldPerSec * WT.bagRatio[단계-1] * EffTerm
```

- **상수** (index = 단계 − 1)
  - `WT.bagRatio = { 0.004, 0.0054, 0.0106, 0.0134, 0.018, 0.025, 0.037, 0.05 }` — 기준 배치에서 방치 시간당이 플레이 시간당의 몇 배인지
  - `WT.bagRefGoldH = { 30364, 22773, 62991, 72739, 90829, 82246, 134055, 156570 }` — 기준 배치 골드/시간(`WT.bagMul` 없이 계산). 기준 배치는 **진화 직전 배치를 새 단계로 옮긴 것**이다. 꼬마 max(1, 단계−1)명, Lv10, 각성 0, 나이테 10, 장식·노드 없음이고 배치 규칙은 B-0과 같다.
  - `WT.bagEffMax = 4`
  - `WT.bagRoundGap = 30`
- **효율항을 이렇게 정한 이유**
  - 기준보다 약하면(x ≤ 1) 그대로 비례한다. 꼬마가 적거나 레벨이 낮으면 확실히 덜 받는다.
  - 기준보다 강하면 제곱근으로 줄인다. 강화가 계속 보이게 하면서(각성 ×1.3 → ×1.14, 꼬마 Lv10→20 ×1.47 → ×1.21) 상한으로 천천히 다가간다.
  - 상한 4는 꼬마·장식·노드를 모두 최대로 했을 때(x ≈ 15~19)에만 닿는다.
- 기준 배치를 "단계 s명 꼬마"가 아니라 "s−1명"으로 잡은 이유는 진화했는데 보따리가 줄어드는 일을 막기 위해서다.
  - 2단계는 줄기 구역이 열리지만 이슬 꼬마(균사석 15)가 없다. 이때 s명 기준이면 효율이 0.39가 되어 진화 직후 ×0.57로 **줄어든다**. s−1명 기준이면 진화할 때마다 ×1.09~1.13으로 오른다.
  - 새 꼬마를 데려오면 효율이 1을 넘어 더 오른다.
- **WT.bagMul 처리**: 골드에서는 빼고 **균사석·개수(`r.gem`·`r.n`)에만 남긴다.** 골드의 단계 성장은 `bagRatio`가 맡는다. 균사석은 B-3의 날 수(진화 균사석 4.5일)를 그대로 둔다.
- **기준이 아직 없을 때** (`lastNormalGold <= 0`): 보따리 골드는 0이고 균사석·개수는 그대로 쌓인다.
  - 세계수는 스테이지 5 이후 열리므로, 새 게임에서 이 경우는 생기지 않는다. 일반 판을 4번 이상 끝낸 뒤라서다.
  - 이 필드가 생기기 전 옛 저장은 다음 일반 판 한 번으로 채워진다.
  - `lastNormalSec <= 0`(이번 필드가 생기기 전 저장)이면 30초로 본다(판 간격 60초). 실제 판 간격(48~74초)보다 길게 잡는 쪽이라 보따리가 적게 나온다. 안전한 쪽이고, 다음 일반 판에서 채워진다.

## Z-3. 근거
1. **1단계는 8시간에 판 1~2.4개.** 지금 판 46개(사용자 지적 "10배 넘음")를 1/20로 줄였다.
   - 숲 구간(스테이지 5~11)에서는 한 판 수입으로 노드를 0.06~1개 산다(R3-17·R4-4: 판 1~12 구매 1~2개/판, 판 10~19 가격 = 판 수입 0.06~0.3판).
   - 그래서 8시간 보따리가 구매 1~3건을 넘지 않게 **판 ≤ 3개**를 상한으로 잡았다. 이러면 초반은 "직접 몇 판 하는 게 밤새 방치보다 크다"가 된다.
   - 숲 판 1개는 1분 남짓이다. 5분만 해도 8시간 방치를 넘는다.
2. **단계가 오를수록 방치 비중이 커진다.** 기준 배치에서 방치 비율은 0.4% → 5.3%로 ×13이다. 진화할 때마다 ×1.09~1.13으로 오르고, 그 단계 안에서도 새 꼬마·나이테로 ×1.2~1.8이 더해진다.
   - 8단계에서 8시간 보따리는 판 16~21개(기준)에서 판 43~78개(강화)다. 판 1개가 74초이므로 플레이 20~95분어치다. "어느 정도 방치해도 주는 보상"이 된다.
3. **최대에서도 방치 ≤ 플레이의 20%.** 상한은 25%로 잡았고 근거는 셋이다.
   - 사용자 원칙 "최대치에서도 비슷해지면 안 된다"를 "플레이가 방치의 4배 이상"으로 옮겼다. 보따리가 플레이 중에도 쌓이는 것까지 넣으면 5배다.
   - 레퍼런스 방치형의 오프라인 수입은 대개 일부만 주거나 시간 상한을 둔다. Egg Inc.는 오프라인 보관 2시간으로 시작한다(조사.md 166줄, 사실). Cookie Clicker는 오프라인 생산이 5%에서 시작해 천국 업그레이드로 오른다([기억, 미확인]). 게임별 비율 표는 theory#6(research)에 아직 답이 없다.
   - 판 수입은 플레이해야만 오르는 값이다(`lastNormalGold`). 방치는 기준을 올리지 못하므로 "스테이지를 할 이유"가 구조적으로 남는다.

## Z-4. 가정
- 판 간격은 2회차 기록(`round2_fit4`, BASE_TIME 15)이다. R3 이후 BASE_TIME이 10이라 실제 판이 5초쯤 짧다. 그러면 "8시간 = 판 개수"가 약 +7~10% 늘어나고 시간당 비율은 그대로다(공식이 시간당으로 정의되어 있어서).
- 기준 배치·최대 배치의 수확량은 `bag_model.py`의 대표 배치 규칙(B-0)을 따른다. 장식·노드 최대 배율 3.94는 곱셈 근사이고, 슬롯 수 제한과 성장·이동 장식의 처리량 효과는 뺐다. 실제 최대는 ±30%다. 상한 4가 걸려 있어 8단계 최대 비율은 거의 바뀌지 않는다.
- "플레이 시간당"은 판 + 30초 기준이다. 상점·세계수 화면에 쓰는 시간까지 넣으면 실제 플레이 시간당은 더 낮다. 그만큼 방치 비율은 표보다 높아진다(30초 대신 60초면 최대 20% → 약 27%). 25%를 넘을 수 있으니 테스트에서 실제 판 간격을 확인해야 한다.
- 봇 시뮬·가격표는 보따리 수입이 0이라고 보고 있다. 이 안에서 플레이 중 보따리는 판 수입의 0.4~5%(기준 배치)라 2회차 진행 목표(R20·R88·R172) 영향은 1판 아래로 본다.

## Z-5. 위험
- **운 좋은 한 판이 기준이 됨**: `lastNormalGold`는 직전 한 판이다. 황금 버섯·축제가 터진 판 뒤에 8시간 자리를 비우면 그 판 기준으로 받는다. 숲~밤의 판 수입 흔들림은 같은 스테이지에서 ×1.5~2이므로 보따리도 그만큼 흔들린다.
  - 막고 싶으면 `lastNormalGold` 대신 평활값을 쓴다. 예: 새 필드 `bagBaseGold = 0.7 × 이전 + 0.3 × 이번`. 필드가 하나 더 늘어나므로 **선택**으로 둔다.
- **소급 적용**: `BagSettle()`은 지난 구간 전체를 "정산하는 순간"의 비율로 계산한다.
  - `lastNormalGold`를 바꾸기 직전에 `BagSettle()`을 불러야 판 중 구간이 새 기준으로 소급되지 않는다(적용안 3). 복귀 때는 `App.cs:116`·`FarmEnsure`가 판보다 먼저 정산하므로 괜찮다.
  - `Game.cs:141`(노드 구매 전 정산)은 이미 있다. `gm_herb`가 효율항으로 들어가므로 그대로 필요하다.
- **기준 배치 상수가 세계수 수치에 묶임**: `bagRefGoldH`는 지금 `Defs.Farm.cs`(TREE_MUSH 골드·시간·슬롯·꼬마 특성)로 계산한 값이다. 이 수치를 바꾸면 `bag_z2.py`를 다시 돌려 배열을 갱신해야 한다. 안 하면 효율 1의 의미가 어긋난다.
- **하루 총량**: 강화 최대에서 하루 16시간 방치는 플레이 3.2시간어치다(16 × 0.2). 하루 1시간만 하는 플레이어에게는 방치 몫이 플레이보다 커진다.
  - 시간당 기준은 지키지만, 사용자가 "하루 총량"으로 판단한다면 `bagEffMax`를 3으로(8단계 최대 15%) 낮추면 된다.
  - 기준 배치(5.3%)라면 하루 0.85시간어치다.
- 화면: `FarmTabWindow`(344줄 근처)의 시간당 표시와 `ReturnPopup`은 `BagRate()`를 그대로 쓰므로 바뀐 값이 자동으로 보인다. "직전 판 골드 기준" 같은 설명 한 줄은 선택이다.

   그리고 새 함수를 추가한다.
   ```
   // 보따리 골드/초: 직전 일반 판 골드/초 × 단계 비율 × 효율항(기준 배치 대비, 1 위는 제곱근·상한 bagEffMax). 판 기록이 없으면 0
   static double BagGold(double raw)
   {
       if (raw <= 0 || G.lastNormalGold <= 0) return 0;
       int i = Math.Min(Stage(), WT.bagRatio.Length) - 1;
       double sec = (G.lastNormalSec > 0 ? G.lastNormalSec : 30) + WT.bagRoundGap;
       double x = raw * 3600 / WT.bagRefGoldH[i];
       double eff = x <= 1 ? x : Math.Min(WT.bagEffMax, Math.Sqrt(x));
       return G.lastNormalGold / sec * WT.bagRatio[i] * eff;
   }
   ```
5. 확인(test): 세계수 1·4·8단계 저장에서 8시간 보따리 골드 ÷ `lastNormalGold`가 표의 "기준 배치" 열(판 2.4·5.5·19.6개, 실제 판 간격으로 환산)과 맞는지 본다. 실제 판 간격(판 끝 → 다음 판 시작)의 중앙값도 잰다.

## R2-1. 보스 관문 판정 공식 (a) — 관리자가 BalanceSim에 넣은 식 (14:43 공유)

```
HP  = st.bossHp
A   = st.atk × st.heavyMul × st.bossMul × (1 + st.crit × (st.critMul − 1))
H   = H0 × st.spdMul × (1 + KB × (핀볼 수 − 1)) × (움직이는 버섯이면 MOVER_H) × (천사가 아니고 임시 수확기 원천이 있으면 1 + TAU)
T   = st.duration − T0                         (보스 날씨: 폭우 spdMul ×0.8, 한파 −3초는 st에 이미 들어 있음)
t   = 청소부: HP / (A·H − HP × CLEANER_HEAL/CLEANER_INT)   (분모 ≤ 0이면 불가)
      환상:   1.99 × HP / (A·H)
      그 밖:  HP / (A·H)
처치 = t ≤ T,   처치 판 길이 = t + T0 + 1.5초
```

### 5) 판 단위 가격 맞추기가 진동한 이유 (`round2_fit1/balance_job.log`, 옛 곡선) — 가설과 제안

로그 요약: 홀수 반복(쌈)과 짝수 반복(비쌈)이 번갈아 나왔다. 쌈은 기간 수입 8~11경(1e17)에 1단계 R19~31, 트리 R56~81이었다. 비쌈은 수입 23억~3,010억에 1단계 R101~159, 2·3단계 미완료였다. 10번 내내 이 2주기가 줄지 않았다.

1. **고정점 반복의 기울기가 −1보다 가파르다 (주원인).** `TunePricesTiers`는 "새 가격 = 직전 실행 수입"을 log 감쇠 d = 0.5로 섞는다. log 가격 x에 대해 수입 log g(x)의 기울기를 −k라 하면, 반복의 배율은 1 − d(1 + k)다. 로그에서 반복 2(가격 최댓값 59.6T)에서 반복 3(848B)으로 갈 때 가격은 −1.85자리, 기간 수입은 6.3e10 → 8.4e16(+6.1자리)였다. 그래서 k ≈ 3.3이다(반복 1 → 2도 +2.4자리 / −6.2자리로 k ≈ 2.6). 가격 최댓값을 단계 수준의 대리값으로 쓴 근사다. 배율은 1 − 0.5 × 4.3 = **−1.15**다. |배율| > 1이라 2주기 진동이 줄지 않는다(관측과 일치).
2. **k를 키우는 것 두 가지.**
   - ① **보스 관문 계단.** 조금 비싸면 30·40 보스에서 멈춰 다음 지역(×10·×100 수입)에 못 간다. 그러면 수입이 자릿수로 떨어진다. 국소적으로는 k가 무한대인 계단 함수다.
   - ② **측정 창에 트리 완료 뒤 수입이 들어간다.** 쌀 때는 R56~81에 트리를 끝내고, R172까지 75·105 지역(×10씩)에서 번 수입이 단계 3 가격을 정한다. 그래서 다음 반복이 크게 비싸진다.
3. **합격 창이 시드 퍼짐보다 좁다 (진동과 별개로 수렴을 막음).** JudgeTiers는 가장 빠른 시드 ≥ 0.8 × 목표, 가장 느린 시드 ≤ 1.1 × 목표를 요구한다. 단계 1이면 R16~22로 폭이 6판이다. 그런데 목표 근처 반복에서도 시드 3개가 R19~27 · R20~25 · R22~26으로 5~8판 퍼졌다. **가격이 맞아도 판정이 통과할 수 없다.**
4. **제안 (코드는 관리자, 값은 제안).**
   - (a) **단계별 차례 이분.** 단계 t의 가격 배율 s_t 하나만 움직인다. 단계 안 모양은 TunePricesTiers가 낸 상대 가격을 쓴다. 단계 1부터 [쌈, 비쌈] 괄호를 잡고 기하평균으로 이분한다. 완료 판이 목표 창에 들면 고정하고 단계 2, 단계 3 순서로 간다(뒤 단계 가격은 앞 단계 완료 판에 거의 영향이 없다). 완료 판이 s_t에 단조라 수렴이 보장된다. "초반은 쌈 + 후반은 비쌈"이 같이 나와도 단계마다 따로 이분하므로 문제가 없다(15:35 이분을 끈 이유를 해결한다).
   - (b) 고정점 반복을 남긴다면 **d ≤ 0.3**(k 3.3이면 배율 −0.29로 수렴)과 **한 반복당 단계 배율 변화 ×/÷ 3 상한**을 둔다. ①의 계단 때문에 d만으로는 부족할 수 있어 (a)를 우선한다.
   - (c) **측정 창:** 단계 t 목표 가격에 쓰는 누적 수입은 `ends[t]`까지만 쓴다(지금도 L = ends[3]). 여기에 더해 **그 시드의 트리 완료 판(doneR[3]) 뒤 수입은 직전 판 수입으로 고정**해 ②를 끊는다.
   - (d) **판정:** 가장 빠른/느린 시드 대신 **시드 중앙값**이 [0.8, 1.1] × 목표 안이고, 가장 느린 시드 ≤ 목표 + max(5판, 0.15 × 목표)이면 합격으로 한다.
   - (e) **시작점:** 지금 DB 가격 × theory 단계 배율(단계 1 ×0.41 · 2 ×0.44 · 3 ×3.8, `theory_r212.json` `tier_scale`). 반복 1(DB 가격)의 "1단계 늦음 · 3단계 매우 이름"과 방향이 같다. 2단계는 시뮬에서 이른데, 3단계가 너무 싸 벽이 사라진 결과라 3단계를 고치면 같이 늦춰질 것으로 본다.
   - 새 곡선의 영향: 보스 처치가 "IV 한 레벨"이 아니라 DPS 연속 성장에 걸리므로 ①의 계단이 조금 무뎌진다. 지역 ×10 계단은 그대로라 (a)~(d)가 여전히 필요하다.

## 2. 근사식과 오차

### 2-1. 구매 복원
T2 시드 1~3과 표본 밖 시드 4~6 모두 판별 구매 수와 끝 상태가 시뮬과 같다(불일치 0판).

### 2-2. 판 수입 근사 (3판: 지역별 상수 추가)

```
log10 I = log10[ Z · (s̄ + 타격점수고정값) · T · 콤보계수 ] + c + β·log10 B + γ·log10 C + δ·스킬수 + (밤 a1 | 들판 a2 | 바다 a3)
```

| 항 | 3판 (지역 상수 있음) | 2판 (없음) | 비고 |
|---|---|---|---|
| s̄ | 0.5 | 0.5 | 격자 0.1~10 안쪽 |
| 콤보 항 | 계수에 비례(κ→∞) | 같음 | κ는 정할 수 없다. 100부터 ∞까지 RMSE 차이가 0.0002 |
| β 핀볼 · γ 군락 · δ 스킬 | 2.03 · 0.40 · ×1.23 | 1.08 · 1.07 · ×1.32 | 진행 중 같이 늘어 서로 섞여 있다. 묶음으로만 쓴다 |
| 지역 상수 밤 · 들판 · 바다 | **×1.89 · ×2.37 · ×1.14** (지역 배율 ×10 위에 더해지는 몫) | — | 새 지역의 버섯 종류·등급 몫으로 보인다 |
| RMSE 적합 (T2 시드 1~3) | **0.242** | 0.271 | |
| **RMSE 표본 밖 (시드 4~6)** | **0.317**, 평균 편향 −0.012 | 0.346 | 맞출 때 안 쓴 기록 |
| 지역별 편향, 적합 → 표본 밖 (숲·밤·들판·바다) | 0 → +0.02 · −0.02 · **+0.03** · −0.07 | −0.10 · +0.07 · **+0.11** · −0.11 → −0.08 · +0.05 · **+0.15** · −0.18 | **들판 과소(verify 지적 ×0.7)는 2판에서 표본 밖 ×1.41까지 컸고, 3판에서 ×1.07로 줄었다** |

### 2-4. research 확인 — "구간 증가율 합산 10^7.8 vs 필요 10^8.4 (0.6자릿수 부족)"
`decompose.py`로 R1 → 완료 판의 수입 성장을 항별로 나눴다. spec T1이 research가 본 기록이다.

| 항 (자릿수) | spec T1 (R1 → R97) | tuned T2 (R1 → R75) |
|---|---|---|
| 지역 ×10^지역 | 3.00 | 3.00 |
| **스테이지 1.01^(판−1)** | **0.41** | **0.32** |
| 타격 점수 (s̄ + 고정값) | 3.12 | 3.05 |
| 라운드 시간 · 콤보 계수 | 0.39 · 0.57 | 0.39 · 0.65 |
| 핀볼 · 군락 · 스킬 | 1.30 · 0.05 · 2.04 | 1.23 · 0.28 · 1.24 |
| 지역 상수 | −0.1~+0.3 | 0.06 |
| **구매로 생기는 성장 합** | **7.47** | **6.84** |
| 모델 합 / 실측 (시드별) | 10.8 / 11.2 (시드 3은 들판에서 끝나 10.2 / 10.1) | 10.2 / 10.9~11.1 |

- 결론: **0.6자릿수는 빠진 성장원이 아니다.** 대부분 `ZoneMul`의 스테이지 항 1.01^(판−1)(R97까지 0.41자릿수)이다. 이 항은 구매가 아니라 판 번호에서 나오는데 research 계산에는 없었다. 나머지 0.2~0.4자릿수는 양 끝 판 수입 한 개씩의 운이다. 판 수입은 판마다 ×2 안팎으로 흔들린다.
- 따라서 research 표의 증가율(구매 성장)과 지역 ×10 세 번은 서로 더해지는 구조이고, 거기에 스테이지 항이 붙는다고 읽으면 된다. 필요한 구매 성장은 8.4가 아니라 약 8.0자릿수(spec)다.

읽은 것 (2판 결론 수정):
1. **들판 보정 뒤 가격만 올린 안(O1)은 ×2.24에서 R93이다.** 2판의 "×2.08이면 R104"는 들판 과소 탓이었다. verify 근사(같은 ×2.08에서 R89~91)와 이제 맞는다. 바다 진입은 완료 4판 전(R89)이라 "바다 = 거의 완료" 문제는 그대로다(verify (b)와 같은 결론).

3. **P6 분해 (verify 수정 요청 3):** 가장 큰 뜀은 모든 안에서 밤 진입 직후 묶음(R21~25 또는 R26~30)이다. 그 비를 지역 배율 몫과 나머지(구매 몫)로 나누면 다음과 같다.

   | 안 | 최대 뜀 | 지역 몫 | 구매 몫 |
   |---|---|---|---|
   | O1 | ×453 | ×10.5 | ×43 |

4. **σ 민감도 (verify 수정 요청 2):** 가격을 올린 안에서는 잡음을 빼면 완료가 4~10판 늦다(σ×0이면 R101~104). "tuned는 잡음에 둔감"은 T2에만 맞다.
5. 해금 판을 옮기는 것(O5)은 진입을 공격력이 정하므로 효과가 없다. 오히려 무구매 최대가 5판으로 나빠진다.
